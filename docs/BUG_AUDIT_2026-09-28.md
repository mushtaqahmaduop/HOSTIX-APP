## Fix log

- **Fix 1 (2026-09-28): one press, one save.** `submitOnce(key, fn)` in `utils.js` — a second call with the same key while the first runs gets the running promise instead of running again; the pressed button is disabled + `aria-busy` until it settles; validation returns and failures free the key. Applied to 14 entry points: `payBulkMarkPaid`, `generateMonthlyRents` (concurrent calls share one run), `markPaymentPaid`, `markPaymentPaidFromStudentView`, `submitPaymentForStudent`, `submitAddPayment`, `submitEditPayment`, `submitReversePayment`, `submitCancellationSettlement`, `submitOwnerFund`, `submitReverseOwnerFund`, `submitExpense`, `submitAddStudent`. Keys carry the record id where two different records may be worked at once. Regression: `tests/submit-once.test.js` (7), `tests/double-submit.spec.js`; 56 e2e across payments, cancellations, concessions, expenses, owner funds, handovers, ownership, mess, students, audit scenarios — all pass.
- **Fix 2 (2026-09-28): closing a question is a No; no stuck flags.** `closeModal()` now runs a still-open question's Cancel callback (×, Escape, outside click); the buttons go through `_confirmYes/_confirmNo`, which take their callback first. `window._updatePendingAP` and `window._updatePendingPS` removed — the "pending record exists" question is always asked (OK updates in place and never re-entered). `window._forcePayPS` replaced by an explicit `submitPaymentForStudent({force:true})` from the question's OK. (`window._forcePayAP` is never set true anywhere — dead, left.) Regression: the × test in `tests/double-submit.spec.js`; 76 e2e across payments, expenses (delete-from-form Cancel reopens the form, now also on ×), cancellations, permissions, students, issues, settings, concessions, handovers, backup — all pass.
- **Fix 3 (2026-09-28): a student number is never handed out twice.** `nextStudentId()` is now one past the highest number EVER used: students on file, every record that names a student (`STUDENT_REF_TABLES` — payments, archive, ledger, cancellations, concessions, room shifts, check-in, fines, complaints, issues incl. `raisedById`, bill splits), and a never-decreasing counter `DB.settings.studentSeq`. `nextStudentId()` only looks (the form preview); `noteStudentId()` records a number when a student is saved (Add Student ×2 paths, Excel import) and in the boot renumbering, whose pass 2 also starts past every referenced number now. **Not done:** a hostel that already hit BUG-008 has a student sharing records with a deleted one; the records carry no creation link to tell them apart automatically — needs a manual check where a student's payments predate their join date. Regression: 8 unit + 1 e2e across a restart; 45 e2e (students, onboarding, demo, admit-to-payment, auth migration) pass.
- **Fix 4 (2026-09-28): one safe restore.** `importBackupData()` (storage.js) is the only restore: shared `validateBackup()` + size limits → `db:importFull` (validate, `*.pre-restore-*.bak` snapshot, one transaction) → reload from disk → ledger rebuild if empty → handover sync. File → Import, the Backup page's Restore and Restore-from-pasted-JSON all call it (the page records the safety copy's path in its restore history). `db:importFull` now accepts both key spellings (BUG-010). Regression: `tests/restore-safety.spec.js`; 25 e2e (backup page, hostile input, main guard, db recovery, save atomicity, write failure, owner funds) pass.
- **Fix 5 (2026-09-28): expenses are red everywhere** (owner's decision). `expenseColor()` (utils.js) reads the `dh-red` tone — the Needs Action pending-payments red — so every expense chart and key shares one colour and follows the theme: dashboard trend (already red, now via the helper), Reports Financial Performance bars and legend (were `--warning-solid` amber), and the Expenses tiles in Settings → Data Management (were `dh-amber`, ×4). Owner Funds "owner took" stays amber on purpose — it is not an expense, which is the point of that feature; the owner can say otherwise. Measured: bars #C0402F light / #F0796A dark, legend identical. 31 e2e (reports, dashboard, settings, chrome) pass.
- Colour-audit finding logged, not fixed: Settings → Data Management gives the same record types different hues in its three tile groups (Payments blue in one, green in another; Students violet / green).
- Found while fixing: `window._forcePayPS` in `submitPaymentForStudent` (the "already paid, charge again?" question) uses the same stuck-flag pattern as BUG-001 — folded into fix 2.
